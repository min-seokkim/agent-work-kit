# Design

Project scope and accepted decisions. Read this before changing the architecture or adding a capability. Superseded decisions remain identified in the table so their reasons are recoverable. Current implementation is summarized in [Development](development.md); proposed work belongs in the [roadmap](roadmap.md).

## Scope

Agent Work Kit is a public project. It has three layers:

| Layer | Content | Why it exists |
|---|---|---|
| Baseline workflow | A short default procedure for any task: define it, do it, check a frozen version, report with evidence. Written as what to do, with the reason. | The kit needs a coherent way of working, and new situations have nothing else to fall back on. Overlap with other projects is fine. |
| Situation guards | Guidance loaded only when its situation arises (skills where the agent supports them), hooks, and `awkit` checks. | Each prevents an entry in [kit/failures.md](../kit/failures.md) and needs a recorded occurrence and a check. |
| Failure catalogue | [kit/failures.md](../kit/failures.md). A reference shipped with the kit, not read every session: read when a guard names an entry as its reason and when designing a guard. | Says what the kit is for, chooses the guards, measures whether they catch anything, and shows what to remove. Its table of guards per entry is generated from the guards' own declarations. |

Overlap with other projects such as superpowers or spec-kit is decided by whether the kit's users need the piece, not by whether another project has it. Overlapping text is kept short and written so it does not conflict when used together with those projects.

The tool's core loop supports the workflow and the guards: fix the input, run the project's checks on it, retain the evidence, compare later results with what was accepted.

The project environment keeps running agents, builds, tests, services, deployment and hosting. awkit connects to the project's existing commands and records identifiers and evidence: which revision was checked, with which command, with what result.

A new situation guard needs a failure entry it prevents, with a recorded occurrence, and a check that would have caught that occurrence. Baseline workflow text needs a step of the default procedure it describes and stays within the every-session word limit. Any new feature also needs a reason the existing commands cannot be extended, a way to see the target version, the result and the cause of failure, and tests for its important failure paths. Kit text that is neither baseline workflow nor a guard for a listed failure moves to the reference; nothing is removed until real use shows it unused, because only use shows which sections are needed. A check runs without the agent choosing to and an instruction does not, so a guard that can be a check becomes one. Measure effect by time to finish, rework, usage and defects found after acceptance, never by the number of features or roles.

### Principles, methods and verification

The owner selected a planning direction that separates common safeguards from task-dependent methods. Purpose, reader, factual fidelity, authorization and agreed author choices remain common. Drafting language, source transformation, explanation order, handoff packaging and review arrangement are methods to choose for the work. Genre informs that choice; it does not prescribe one method for every document of that kind.

Assess a procedure by its contribution to the usable result as well as its burden. A supported improvement can narrow an obligation, make a step optional or replace a method. Reuse existing records and tools where they help; their existence does not establish fitness for every task. Automated checks establish the properties they inspect. Voice, reasoning and reader understanding require the applicable reading or use evidence.

The [method-selection review](history/tasks/writing-revision-workflow.md#method-selection-review) owns the writing-specific changes to consider and their acceptance conditions. This decision authorizes planning integration; shipped guidance and enforcement change through a scoped implementation with its own evidence.

### Evidence storage and continuity across environments

The owner authorized the coordinator to integrate the scope assessment and choose subsequent work. Storage efficiency is the first selected unit; the [task record](tasks/review-storage.md) distinguishes inspection from later changes to storage. Retain each run's identity, checked inputs, outcome, logs and artifact associations. Identical immutable payloads may be shared when readers can still retrieve and verify the exact evidence. Any such implementation must preserve existing evidence paths or provide an explicit compatible migration. Shared storage does not authorize deletion or retention expiry.

The desktop execution host and laptop file-access client are the selected environments for later continuity evaluation. A task needs a stable project and request identity, a known execution host, corresponding paths and declared client capabilities. Inspect retained execution state after interruption before retrying a change. Apply the existing provider-parity decision and record unsupported operations explicitly; shared file access alone does not establish remote execution or safe database access.

Shared-context discovery remains a candidate extension of existing scan/doctor commands. Link the configured shared entry point and the project's current task record, preserving their owners and locations. The existing decision against writing memory files remains in force. Separate current facts, historical activity and open handoffs when reporting what to read. Provider-memory divergence is an observation question until a recorded occurrence justifies a guard.

## Decisions

| Decision | Detail |
|---|---|
| Verify local-state exclusion at write boundaries | Project-managed `.awkit` writes establish clone-local Git ignoring without prior initialization. Use anchored project-relative rules, coordinate awkit append/restoration and preserve unrelated bytes. Explicit writers stop on failed protection or a tracked selected output before payload or native startup. Hooks skip unsafe persistence while retaining their host decisions. Retained runtime records keep exclusion; runtime rules acquire no inferred setup ownership. Non-Git use, no-Git setup, home installation, external outputs and read-only paths retain their existing boundaries. See the [local-state task](tasks/local-state-exclusion.md) for scope and delivery evidence. |
| Provide comparable provider support through shared session controls | When adding a Codex session capability, assess and provide the comparable Claude path where supported. Shared interfaces follow declared capabilities, while unsupported operations carry reasons. Preserve native permission, configuration-observation and ownership distinctions; matching labels do not establish equal semantics. The [provider-parity task](tasks/session-orchestration.md#selected-provider-parity) records the owner's direction and first implementation. This is a project design requirement, not a new global kit guard. |
| Compare writing findings without changing the full-file policy | The [writing-comparison contract](tasks/writing-comparison.md) adds an explicit two-revision report to the existing check group. A separate envelope preserves the legacy writing JSON and command behavior while carrying source identities, occurrence correspondence and uncertainty. Existing findings remain visible and still fail when they are errors. The first interface uses selected same-path regular Markdown blobs; automatic baseline selection and inferred renames are deferred. Implementation and delivery state belong in the task record. |
| Separate usage observations from exact interaction counts | Format 3 in `7977b35` retains supported human-input observations while leaving an exact count unknown when representation or identity is ambiguous. Token/log coverage is separate. Codex's existing model-context row count is not a unique-turn or API-call count. The [usage contract](tasks/usage-log-compatibility.md) owns migration details and remaining validation. |
| Require an explicit result contract for bundled hook commands | An unknown command can share a return code with a real violation and consume the rule's one-block state. The [planning trial](tasks/planning-implementation.md) authorizes an opt-in pass/finding/error protocol and bounded adapter, with custom commands preserved. Execution errors must be visible and leave later checks available. Existing project rule copies migrate deliberately, after capability verification; a matching package version is insufficient. |
| Another repository inside a project is not supported | A clone of awkit, or any other repository, inside a user's project would need submodule handling and checks across several repositories. awkit warns instead (`doctor`, `kit scan`, `check done`) and tells the user to move or ignore it. |
| Git is required | The review commands work on Git-tracked files. Non-developers get an easy install path instead of a Git-free mode (see [completed setup work](history/evidence.md#completed-work)). |
| Web-only tools are extras | `pipeline`, `publish` and `ui` are useful mainly for web projects. They live in `src/awkit/extras/` with their command names unchanged and are not mentioned in the READMEs. If real use does not need them, they leave the package. |
| Public project; baseline workflow plus failure guards | See [Scope](#scope). The failure catalogue chooses and measures the guards; agents receive the baseline workflow and the guards, written as what to do. This replaces the earlier plan to split the kit into `dev` and `work` profiles chosen at install time. |
| One repository, one package | Unchanged. |
| Keep independent-session collaboration in awkit | The owner finds the current local channel useful and lightweight. Preserve collaboration between providers so independent sessions can contribute different judgments while keeping their own context. Maintain the SQLite/CLI implementation without adding a third-party collaboration project as a dependency. Learn from external designs; add capabilities when actual work needs them. See the [collaboration plan](tasks/independent-session-collaboration.md). |
| Restrain the kit's length | Limits by when a file is read, in `tests/test_kit.py`: the files read at the start of every session (kit README, `workflow.md`, project profile) together stay within 2,000 words, which is what Claude Code's documentation recommends for CLAUDE.md (about 200 lines); every other file is read when its situation arises and stays within 3,500 words, about the 5,000 tokens that survive a context compaction whole. There is no total: an agent never reads the whole kit at once, and the number of rules is held down by requiring each section to serve the baseline workflow or a failure entry. |
| Agents are the readers | See [AGENTS.md](../AGENTS.md#working-rules). |
| Hold the first release | Until the [release conditions](release.md#release) are met. |
| The failure catalogue ships with the kit | It moved from `docs/` to `kit/failures.md`. It is the document that best says what this public tool prevents; the owner's records and the guards' declarations keep adding to it; and the hook runner planned next shows which entry a rule enforces, so users need the entries where the rules run. The worry that agents would read it as a list of prohibitions applies to files read every session, and this one is a reference read when a guard points to it. Its table of guards per entry is generated from a `Prevents:` line in each guide section and a `PREVENTS` declaration in each command's code, and a test fails when the table is out of date. |
| No further investment in the done check | Other tools already check done reports. `check done` stays as it is. It trusts exit codes, so a test changed to pass is not caught; the reference says so. |
| `dev` is an install source | Users and the installers install from `dev`, so its history is never rewritten and never force-pushed. A session with local commits fetches and rebases them onto `origin/dev` before pushing. |
| Use what a project has instead of adding beside it | Most projects the kit goes into already have CLAUDE.md or AGENTS.md, rule files, skill bundles such as superpowers, hooks, memory (Claude Code's automatic memory, MEMORY.md, Beads, `.planning`) and their own commit conventions. Copying the kit folder beside them said the same things twice, and nothing a session read pointed at the copy: `workflow.md` and the profile reached an agent only when someone wrote that into the project's instructions by hand, as this repository did. Four principles, each enforced in code and tests (`tests/test_connect.py`). Read before adding: `kit scan`, `init`, `skills` and `hooks` read the project's instruction files, skills, bundles, hooks, memory and completion gates first, and a bundle or gate that already does a job leaves the kit's version out. Add nothing that is always on: the only text in every session is a section of about 70 words at the end of the existing instruction file and one line per skill, and `kit scan` reports that count first; a test bounds it at 250 words. The project's place for state is the place: the profile points to where commands, conventions and records are kept rather than copying them, the kit's record templates are the fallback (`protocol.md`), and awkit writes only to `.awkit/`, its skills, its section and its hook entries, never to memory files. Leave cleanly: everything added is recorded in `.awkit/installed.json` and `kit remove` restores each file, byte for byte when it is unchanged. The kit folder copy remains as `kit init --copy`. |
| Three layers: the computer, what a project commits, what stays in the clone | Supersedes the instruction-file section and project skills of the row above. The way an agent works belongs to the person, so it is installed once per computer: awkit, the guides inside the package, and the skills in the user folders (`~/.claude/skills`, `~/.agents/skills`), written by `kit skills` and by the installers. Skills are text, and agents keep only their one-line descriptions in context and read a body when its situation arises, so a user folder costs every project the descriptions and nothing else. A project commits only what finishing means there: `checks.toml` with the `[kit]` table (`version`, `done`, `recipient`, `records`) and `rules.toml`. Hooks run code, so they stay in the clone with `.awkit/`, and nothing that executes is placed in the user folder. `kit init` therefore writes no instruction file, copies no guide and commits nothing; it prints the one line a user may add. `kit guide` prints any guide for agents without skills. awkit writes only to the places in `WRITES` (`src/awkit/connect.py`), checked by `tests/test_layers.py`; `kit remove --project` and `--user` take each layer out. `kit hooks` and its `--remove` belong to the hook runner; init and remove call them as commands. |
| Rules run as hooks, not as prompt text | Instructions in a prompt are forgotten as turns accumulate, taken as optional, or not recognized as applying; in public reports of agent use, a user repeated one instruction twenty times in a session, and what held was hooks and linters. A rule in the prompt also costs context every turn, while a script that reads a tool call costs none until it fires. So the kit's rules move into `rules.toml`, run by `awkit hook` on every hook event of Claude Code and Codex, which share the hook contract. A rule recognizes its situation by the shape of the tool call (tool, shell command, edited path, text written), not by the prompt. The runner is silent when nothing fires, says each line once per session, and errs toward missing: a wrong hook costs trust, a missed rule falls back to the workflow. It logs every firing, so `awkit hook report` can show whether repeated instructions decrease. A silent call takes about 110 ms on Linux, most of it Python's own start; the web extras and `review` are imported only by their commands to keep it there. |
| The writing rule reads the result, not a tool call | Writing can end in the chat with no tool call: the planning session wrote a long Korean instruction for another session without calling the writing skill, the owner pointed it out twice, and no hook had run. The default `writing-reply` rule reads the final reply when the agent stops (Hangul length, a heading or a request for a document) and blocks once when supported transcript evidence shows no guide access. From `fce1d14`, access requires correlated success and returned guide content; uncertainty remains fail-open. This establishes access evidence, not comprehension or writing quality. The [reference](../kit/reference.md) describes the supported shapes and heuristic limits. |
