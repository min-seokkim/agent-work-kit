# Design

Project scope and the decisions a change must respect. Read this before changing the architecture, a file format or a shipped behavior. Each row says what was decided and why. Git history has the discussion that led to it. Work to do is in the [roadmap](roadmap.md).

## Scope

Agent Work Kit is a public project with three layers:

| Layer | Content | Why it exists |
|---|---|---|
| Baseline workflow | A short default procedure for any task: define it, do it, check a frozen version, report with evidence. Written as what to do, with the reason. | New situations need something to fall back on. Overlap with other projects is fine. |
| Situation guards | Guidance loaded only when its situation arises (skills where the agent supports them), hooks, and `awkit` checks. | Each prevents an entry in [kit/failures.md](../kit/failures.md) and needs a recorded occurrence and a check. |
| Failure catalogue | [kit/failures.md](../kit/failures.md), shipped with the kit and read when a guard names an entry. | It says what the kit is for, chooses the guards and shows what to remove. Its guard table is generated from the guards' own declarations. |

The tool's core loop: fix the input, run the project's checks on it, keep the evidence, compare later results with what was accepted. The project environment keeps running agents, builds, tests and deployment; awkit connects to the project's commands and records which revision was checked, with which command, with what result.

A new guard needs a failure entry with a recorded occurrence and a check that would have caught it. Baseline text needs a step of the default procedure and stays within the every-session word limit. A new feature needs a reason the existing commands cannot be extended, a way to see the target version, the result and the cause of failure, and tests for its failure paths. A guard that can be a check becomes one, because a check runs without the agent choosing to. Measure effect by time to finish, rework, usage and defects found after acceptance, never by the number of features.

Common safeguards are separate from task-dependent methods. Purpose, reader, factual fidelity, authorization and agreed author choices are common to every document. Drafting language, source transformation, explanation order and review arrangement are chosen per task; genre informs the choice but does not prescribe one method.

## What the measurements showed

Nine sessions were measured between `6482bc7` and `83db970`; the table is in Git history (`docs/history/evidence.md` at `2ef5040`). This is the conclusion, and it closes the measurement item.

- Repeated instructions fell from 4 of 52 and 2 of 56 user messages, in the two long sessions before the hook runner, to 0 in the seven sessions after it. Those sessions had 1 to 6 messages each, so shorter sessions explain part of the drop.
- Who caught failures changed. Before the runner the owner caught every occurrence (F9 twice, F13, F14, F28) and no guard did. After it, `AGENTS.md` and the `commit-identity` rule refused F9, the baseline-hash recheck prevented an F16, and `done-check` blocked a premature report once.
- Wrong hook firings fell from 3 of 4 and 2 of 2 to 0 of 3 as the rules were fixed. Each wrong block cost the owner a turn, so a rule errs toward missing.
- Most defects were found by installing and using the kit on real projects, not by guards: about twelve kit defects, among them F7, F11, F25 and F29 occurring in the kit itself.
- Cache reads are 95 to 99 percent of every session's tokens. Context size, not output, drives cost. That is the reason for the word limits.
- The column "what the user did not have to do" stayed unknown in seven of nine rows. A value no tool records does not get recorded.
- Not measured, and not measurable here: time saved, and whether the same work without the kit would have failed. The design forbids the comparison run.

The largest cost of the period is not in the table. Over six days (`0e33ff6` to `2ef5040`) sessions authorized to choose their own work built session and storage features no roadmap item asked for, made 19 of 44 commits as record changes only, grew the records to 92,000 words, and once waited three hours for a decision. The owner caught it, not a guard (F28, F12). The guards against it are now the roadmap's Ready table, the record rule in AGENTS.md and the test on `docs/`.

What follows: a guard candidate needs an occurrence in the catalogue, and F11, F16, F21, F22 and F29 have one. The nine entries without one were merged into entries that have one, or removed (F18); F2 and F26 gained occurrences from the CI audit. No new check was built for F16, F21 or F22: each recorded occurrence was lost meaning (dropped conditions, an omitted decision, an inference stated as an observation) that only a reader comparing against the source catches. Their guards are the move-a-whole-topic rule, the handoff fields and review. F11 and F29 already have `doctor` and `kit scan` checks.

## Decisions

| Decision | Detail |
|---|---|
| The agent picks its work from the roadmap | The Ready table in the roadmap is the authorization. Earlier, every item waited for an owner choice, and six days of sessions built unasked features and rewrote records while the roadmap's top items stood still. The owner keeps the Blocked table and the Decided-against list; the agent keeps Ready moving. |
| Four development records, no more | `docs/` holds roadmap, design, evidence and release, with word limits in `tests/test_kit.py`. Task files, history folders and a development entry page grew to 92,000 words in 61 files and were updated in commits that changed nothing else. Git history is the record of what happened. |
| How to measure the kit | Per task, record the failure entries that occurred or were caught and the hook firings with wrong ones counted, both from `awkit hook report` and the catalogue. Count a repeated instruction only when the owner notes one. Never run the same task twice with and without the kit: the second run knows the answer. A firing is not a prevented failure. The five-column table was retired when its last column stayed unknown (see above). |
| Before building a feature, name five things | The user problem and its consequence, the expected improvement, what existing capabilities already cover, the selected change, and the result that would justify keeping it. If research shows current behavior is enough, add nothing. |
| Rules run as hooks, not as prompt text | Prompt instructions are forgotten, taken as optional, or not recognized as applying, and cost context every turn. The kit's rules live in `rules.toml`, run by `awkit hook` on every hook event of Claude Code and Codex. A rule recognizes its situation by the shape of the tool call. The runner is silent when nothing fires, says each line once per session, errs toward missing, and logs every firing so `awkit hook report` can show whether repeated instructions decrease. A silent call takes about 110 ms on Linux; the web extras and `review` are imported only by their commands to keep it there. |
| The writing rule reads the result, not a tool call | Writing can end in the chat with no tool call. The `writing-reply` rule reads the final reply when the agent stops and blocks once when transcript evidence shows no guide access. From `fce1d14`, access requires correlated success and returned guide content; uncertainty is fail-open. This proves access, not comprehension. |
| Three layers: the computer, what a project commits, what stays in the clone | The way an agent works belongs to the person, so awkit, its guides and the user-folder skills are installed once per computer. A project commits only `checks.toml` with the `[kit]` table and `rules.toml`. Hooks run code, so they stay in the clone with `.awkit/`. `kit init` writes no instruction file and copies no guide; `kit guide` prints any guide; awkit writes only to the places in `WRITES` (`src/awkit/connect.py`), checked by `tests/test_layers.py`. `kit init --copy` remains for a copied folder. |
| Use what a project has instead of adding beside it | `kit scan`, `init`, `skills` and `hooks` read the project's instruction files, skills, bundles, hooks, memory and completion gates first; a bundle or gate that already does a job leaves the kit's version out. The only always-on text is about 70 words at the end of the existing instruction file and one line per skill, bounded at 250 words by a test. The project's place for state is the place; awkit never writes memory files. Everything added is recorded in `.awkit/installed.json` and `kit remove` restores it. |
| Restrain the kit's length | Limits by when a file is read, in `tests/test_kit.py`: files read every session together within 2,000 words; a situation file within 3,500 words; the two references within 9,000. No total, because an agent never reads the whole kit. At a reference limit, move a complete topic into its own guide and compare the result with its source before shortening anything; shortening in place lost eight conditions once (F16). |
| Local-state exclusion at write boundaries | Project-managed `.awkit` writes establish clone-local Git ignoring before any payload, SQLite or provider startup, with anchored project-relative rules. Explicit writers stop on failed protection or a tracked target. Hooks skip unsafe persistence and keep their host decision. Non-Git use, home installation and external outputs keep their boundaries. |
| Comparable provider support | A Codex session capability gets the comparable Claude path where supported, through shared controls that follow declared capabilities; unsupported operations carry reasons. Matching labels do not establish equal semantics. Reuse native messaging, queues and sessions first; the SQLite channel is the fallback and the evidence. Never mirror full transcripts. |
| One route per way of reaching a conversation | The controller reaches a session through its own Codex app server, a dedicated connection to an enrolled Codex conversation, or a Claude SDK client. Each is a route in `session_routes.py` with the same operations (connection, resume, dispatch, decide, interrupt), so the controller never branches on the provider and a new mode is one new route. Helper modules use the controller's public methods (`stores`, `connection`, `native_owner`, `event_handler`), never its private attributes. States are declared in `session_states.py`; the store refuses an undeclared session state, and SQL takes its IN lists from the same tuples. |
| Sessions, roles and attempts | A session's identity is separate from its role and task; an independent review needs a separate session, and the reviewer must not have written the reviewed change. Store a send attempt durably before sending; a held or refused message never triggers another transport. Never call a fresh session, a fork or an old-log read "resume". Approving an agent run does not approve every external action it proposes. Before `close`, confirm the delivered tree equals the checked tree and get the recipient's acknowledgement. |
| Shared artifact storage | Opt-in per configuration for new runs: a collection-local SHA-256 object store, not Git-backed and not hardlinks, because Git adds ownership and lifetime problems and editing one hardlinked file would change several runs. Legacy copied runs stay readable; `review export` makes a run independent. Shared storage authorizes no deletion or expiry. Judge adoption by measured growth on needed runs, never by rerunning unchanged checks. If adoption fails, new runs go back to copied mode and old shared runs keep their store. Real records are never migration fixtures. |
| Artifact selection preview | `review preview` shares the collector's selection rules and reads no contents. Matching every pattern does not establish that the evidence is complete; current sizes predict nothing about generated outputs. |
| Writing comparison | `writing compare` adds a two-revision report beside the full-file check, in a separate envelope. Identical bytes match occurrences in order; otherwise a line appearing once in each file with the same rule matches; anything else is unclassified. "Existing" never means accepted. The baseline is chosen explicitly and never moved by a session start, edit or failed run. |
| Usage observations are not exact interaction counts | Format 3 keeps supported human-input observations and leaves the count unknown when representation or identity is ambiguous. Codex's model-context row count is not a turn or API-call count. |
| Bundled hook commands need an explicit result contract | An unknown command can share a return code with a real violation. Bundled commands use an opt-in pass/finding/error protocol; custom commands are preserved. A package fix never rewrites a project's rules: an old setting can be intentional. Repair one project only with authorization. |
| Hook error context is bounded | At most 8 awkit frames from at most 64 traceback links, strings capped at 512/256/128 characters, never argv, env, sys.path, payloads, source lines or locals. Logs get shared, and paths identify users. |
| Other projects get technical feedback only | awkit sessions never plan, review or approve another project's documents. Private prose, paths and conversation IDs stay out of this public repository; public fixtures are fictional and built independently. |
| Document workflow | One workflow for every document, presentations included. `review accept` is not human approval; `review compare` compares bytes and text only. Inspection of a document is read-only: never re-save, run macros or refresh links. Expected values come from the requirements, never from the candidate. A required check that was not run leaves the work incomplete. Hooks detect operations, not words; persuasiveness and visual quality never become blocking scores. One session must be able to finish the workflow; collaboration is optional. Diagnosis and revision are steps, not mandatory agents; a review does not authorize an unrequested rewrite; no preference ledger. |
| Dependencies | Adopt one only after assessing a concrete gap, its license, deployment and maintenance. The Anthropic PPTX skill's license forbids derivatives, so it is reference, not code. No third-party collaboration framework. |
| Git is required | The review commands work on Git-tracked files. Non-developers get an easy install path instead of a Git-free mode. |
| Another repository inside a project is not supported | It would need submodule handling and multi-repository checks. awkit warns (`doctor`, `kit scan`, `check done`) and tells the user to move or ignore it. |
| Web-only tools are extras | `pipeline`, `publish` and `ui` live in `src/awkit/extras/` and are not mentioned in the READMEs. If real use does not need them, they leave the package. |
| No further investment in the done check | Other tools check done reports. `check done` trusts exit codes; the reference says so. |
| No scheduler, no new task store, no general updater | Scheduling stays with the user's platform. Task state reuses the project's own task tool; when records conflict, keep both and never pick by modification time. Reinstalling awkit does not update connected projects. |
| Test fixtures | A Git fixture has its own verified repository root; a non-Git fixture sits outside every ancestor worktree. An installer probe once found the parent repository and wrote a live selector. |
| Formats migrate in place before the first release | No parallel legacy mode; the change is announced in CHANGELOG. There is no released consumer yet. |
| `dev` is an install source | Its history is never rewritten or force-pushed. Local commits are rebased onto `origin/dev` before pushing. |
| Hold the first release | Until the [release conditions](release.md#release) are met. |
| One repository, one package; agents are the readers; the READMEs are for people | The READMEs keep their five sections and basic setup commands; command details belong in the kit. Everything else is written in English for agents ([AGENTS.md](../AGENTS.md)). |
