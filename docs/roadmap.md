# 구현 계획

Agent Work Kit은 에이전트가 실제 작업을 수행하도록 돕는 지침과 실행 도구를 함께 제공합니다. 다음 확장에서는 처음 써보는 절차를 줄이고, 검사한 결과물을 보존하며, 실제 상태를 확인해 작업을 이어갈 수 있게 합니다. 개발, 문서 작성, 자료 조사와 데이터 정리에서 이 기능들을 함께 사용합니다.

2026-10-22 기준 계획입니다. 마지막 커밋, 현재 작업 폴더의 변경, 앞으로 구현할 기능을 구분합니다. [역할과 범위](scope.md)는 기존 제품 범위를 설명하며, 2단계에서 소개 문서와 함께 확장 방향을 반영합니다. 아래에 제안한 새 명령은 아직 구현되지 않았습니다.

## 출발점

계획 작성 시점의 기준 커밋은 `40b6c72`이며 패키지 버전은 `0.2.0`입니다.

| 기능 | 마지막 커밋의 동작 |
|---|---|
| 공통 키트 | 작업 지침, 상태 규약, 프로젝트 적용표와 작업·검토·결정·재개 양식을 제공합니다. |
| 한국어 문서 작성 | 사실과 조건을 보존하고 영어 초안을 거쳐 한국어로 쓰며 사실, 문장, 전체 흐름을 검토합니다. |
| 역할 파일 | 다섯 역할의 지침과 모델 설정을 공급자별 파일로 만듭니다. |
| 검토 스냅샷 | HEAD에 지정한 파일의 변경을 얹은 Git commit 객체를 만듭니다. |
| 격리 검사 | 고정한 버전의 worktree에서 준비 명령과 검사 명령을 실행하고 결과와 로그를 보존합니다. |
| 검토 채널 | 공유 SQLite 파일에 요청, 응답과 반박을 저장하고 대기와 종료를 처리합니다. 읽음 위치는 역할별로 공유합니다. |
| 사용량 집계 | 실행 기록에서 모델과 토큰을 스레드별로 모읍니다. |
| 배포 결과 확인 | 프로젝트 명령을 실행하고 실제 버전과 필수 검사를 확인합니다. 불확실한 상태와 복귀 결과를 구분합니다. |
| 로컬 문서 발행 | 허용 파일과 링크를 검사하고 진입점을 교체합니다. 해시로 확인한 이전 버전을 복원합니다. |
| 화면 검토 시트 | 여러 화면 폭의 캡처와 가로 넘침 검사 결과를 모읍니다. |

계획 작성 당시 미커밋 변경에는 검사 단계별 `cwd`, 실행 폴더 검증, 산출물 보존 예제와 관련 테스트가 있었습니다. 시스템 프로그램, SDK, 펌웨어 등 산출물별 완료 조건을 다루는 적용표와 문서 확장도 포함합니다. 이 변경을 다음 구현의 출발점으로 삼고, 커밋과 릴리스 여부는 별도로 기록합니다.

마지막 커밋에서는 두 문제를 재현했습니다. 문서 링크 검사가 의존성과 생성 파일이 있는 폴더까지 들어갑니다. 사용량 집계는 모델 정보만 있고 토큰 기록이 없는 입력을 받으면 누락 안내 없이 토큰을 모두 `0`으로 표시합니다.

## 구현 순서

| 단계 | 사용자가 얻는 결과 | 주요 변경 위치 |
|---|---|---|
| 0. 기존 변경 정리 | 하위 폴더 검사와 산출물 보존 예제를 안정적으로 사용합니다. | `review.py`, `test_review.py`, `examples/review/`, 기존 변경 문서 |
| 1. 신뢰성 결함 수정 | 문서 검사 범위가 정확해지고, 누락된 사용량과 실제 0을 구분합니다. | `test_kit.py`, `usage.py`, `test_usage.py`, CLI 설명 |
| 2. 첫 실행 경험 | 설치 후 예제 하나에서 실패 확인, 수정과 재검사를 끝냅니다. | 예제 생성 기능, 패키징, CLI, 최소 적용표, README |
| 3. 결과물 보존과 대조 | 어떤 자료로 만든 결과인지 확인하고 검사한 파일을 보존합니다. | 새 `artifact.py`, `review.py`, 문서·데이터 예제 |
| 4. 검토 전달과 재개 | 수신 확인을 구분하고 기존 실행 기록과 실제 파일을 대조해 이어갑니다. | `channel.py`, 새 실행 기록 조회 기능, DB 전환 검사 |

0단계 이후 1단계부터 3단계까지를 첫 배포 묶음으로 잡습니다. 4단계는 DB 전환과 복구 검증을 마친 뒤 별도 배포합니다. 기존 배포 실행기와 문서 발행기의 실패 처리 의미를 보존합니다.

## 0. 현재 변경을 기준선으로 정리

미커밋 diff를 검토하고 검사 실행기 변경, 예제와 문서 변경을 목적별로 나눕니다. 단계별 실행 폴더를 추가하면서 기존 준비 단계 중단 조건, 검사 실패 처리, 시간 초과와 정리 동작이 유지되는지 확인합니다.

Windows와 Linux에서 현재 전체 테스트를 실행하고 wheel 설치 후 명령을 확인합니다. 통과 수와 환경은 이번 실행 결과로 [검증 범위](validation.md)에 기록합니다. 소스 구현, 커밋과 릴리스 상태를 각각 표시합니다.

## 1. 검사와 집계 결과의 신뢰성 수정

### 문서 링크 검사

검사 대상을 저장소 루트의 Markdown과 관리하는 문서 폴더로 명시합니다. `.venv`, `.awkit`, `node_modules` 등 의존성, 생성물과 실행 기록 폴더는 순회 전에 제외합니다. 설치된 키트의 링크 검사도 유지합니다.

외부 패키지에 깨진 링크가 있어도 저장소 검사가 실패하지 않아야 합니다. 반대로 관리 대상 문서에 만든 깨진 링크는 반드시 찾아야 합니다. 이 두 조건을 회귀 테스트로 고정합니다.

### 사용량의 누락 처리

알려진 0, 누락, 일부만 확인한 값과 잘못된 기록을 구분합니다. 확인하지 못한 필드는 JSON에서 `null`로 표시하고, 합계에는 확인된 부분합과 집계가 완전한지 나타내는 정보를 함께 둡니다. 사람이 읽는 표에서도 부분합을 전체 사용량처럼 표시하지 않습니다.

결과 형식에 버전을 붙이고 기존 JSON 소비자가 바꿔야 할 항목을 문서화합니다. 응답 중복 제거와 누적 토큰 처리는 유지합니다. 횟수가 기록된 응답 수인지 턴 문맥 수인지 표시하고, 실제 API 호출 수와 구분합니다.

누락 필드, 명시적인 0, 중복 응답, 누적값, 잘못된 값과 알 수 없는 형식을 모의 로그로 검사합니다. 작성 중인 마지막 불완전한 줄과 중간의 손상된 기록도 구분해서 알립니다. 후속 수집 도구를 연결할 때도 같은 표본과 결과 형식으로 대조할 수 있게 합니다.

**완료 기준:** 토큰 측정값이 없는 세션을 정상적인 0 사용량이나 완전한 합계로 보고하지 않습니다. 기존에 정확히 집계하던 표본의 값은 유지합니다.

## 2. 설치 후 바로 실행할 수 있는 시작 경로

### 실행 가능한 예제

명령 설계안은 `awkit example init documents <새 폴더>`입니다. `data` 예제도 같은 방식으로 선택합니다. 모의 자료, 검사 설정과 짧은 사용 안내를 새 폴더에 복사하며 기존 폴더는 보존합니다. Git 초기화, 스냅샷 생성과 검사 실행 명령을 다음 행동으로 안내합니다. Git 초기화는 사용자가 실행할 명령으로 명시합니다.

- 문서 예제에는 깨진 내부 링크를 넣습니다. 검사 실패를 확인한 뒤 링크를 수정하면 재검사가 통과합니다.
- 데이터 예제에는 필수 열이 빠진 CSV를 넣습니다. 입력을 고친 뒤 가공 결과를 만들고 예상한 열과 행을 검사합니다.
- 예제 파일을 wheel에 포함하고 소스 저장소 밖에 설치한 환경에서 실행합니다. 복사 과정에서는 기존 파일을 덮어쓰지 않습니다.
- Windows와 Linux에서 각각 실행 가능한 명령을 제공합니다. 선행 도구 설치를 포함해 첫 사용 시간을 측정합니다. 5분은 설계 목표로 두고 실제 측정 결과와 구분합니다.

3단계에서 같은 예제에 결과물 보존과 사후 대조를 연결합니다.

### 최소 적용표와 작업 지침

첫 적용표는 원하는 결과, 기준 자료, 수정 범위와 보존 조건, 완료 확인 방법, 결과 위치를 다룹니다. 위임, 모델과 전달 절차는 해당 작업에서 필요할 때 채웁니다. 기존 프로젝트 기록이 있으면 그 위치를 연결합니다.

`kit/workflow.md`, 적용표와 역할 지침을 일반 작업에도 맞게 수정하고 `kit/work-types.md`와 `kit/examples/general-work.md`에 필요한 항목을 골라 쓰는 방법을 담습니다. 조사, 작성, 정리, 앱 조작, 학습과 개발에 맞춰 완료 조건과 개입 방식을 설명합니다. Git은 문서와 코드 작업 모두에서 사용할 수 있게 합니다.

README, [역할과 범위](scope.md), 패키지 소개도 실행 예제와 맞춥니다. 에이전트 대상 문서는 영어로 유지하고 한국어 작성 가이드의 작성·검토 절차를 보존합니다. 공용 예제에는 모의 자료를 사용합니다.

### CLI와 기여 환경

CLI 도움말과 프로그램이 직접 만드는 진단 메시지는 영어를 기본으로 바꿉니다. 명령 식별자, 종료 코드와 기계 처리용 키는 유지하되 사용량 결과처럼 의미가 바뀌는 형식은 버전과 전환 안내를 제공합니다.

Ruff를 개발용 검사에 추가하고 명백한 오류와 import 정리부터 적용합니다. 설정과 결과를 주고받는 함수부터 타입을 명시합니다. 실행에 필요한 의존성은 기존 구성을 유지합니다.

**완료 기준:** 새 환경에서 설치, 예제 생성, 의미 있는 실패 확인, 수정과 재검사, 결과 위치 확인까지 진행할 수 있습니다. 이 경로에서 역할 설정이나 상세 적용표 작성이 선행 조건이 되지 않도록 구성합니다.

## 3. 검사한 결과물 보존과 사후 대조

### 공통 결과물 기능

새 `artifact.py`를 검사 실행기와 독립 CLI에서 함께 사용합니다. 명령 설계안은 `awkit artifact capture`와 `awkit artifact verify`입니다.

`capture`에는 기준 폴더와 포함할 파일 목록을 명시합니다. 선택한 파일의 바이트를 새 결과 폴더에 복사하고 버전이 있는 manifest를 원자적으로 기록합니다. 일반 폴더와 Git 프로젝트 모두에서 사용합니다.

manifest에는 파일의 상대경로, 크기, SHA-256, 확인 가능한 원본 버전, 검사 설정 해시와 연결된 실행을 기록합니다. 날짜는 부가 정보로 취급합니다. 원본의 위치나 식별자를 적는 것과 원본 바이트를 보존하는 것은 구분하며, 원본 복사도 명시한 파일 목록을 따릅니다.

`verify`는 누락되거나 바뀐 파일과 잘못된 경로를 보고합니다. 경로 탈출, 심볼릭 링크와 정션, 파일명 충돌, 복사 도중 변경을 검사합니다. 해시 일치는 파일의 동일성과 무결성을 확인하며 내용의 사실성이나 출처의 신뢰성은 별도 검토 결과로 남깁니다.

### 격리 검사에 연결

검사 설정에 보존할 산출물과 필수 산출물을 명시할 수 있게 합니다. `result.json`, 로그, 결과물은 임시 worktree를 지운 뒤에도 남습니다. 명령이 성공했어도 필수 산출물이 없으면 실패로 처리합니다. 검사 설정의 해시와 함께 실제 설정 파일도 보존합니다.

검사한 파일과 보존한 파일이 같다고 보고하려면 해당 검사 전후의 해시를 대조하거나 검사기가 제공한 해시를 확인합니다. 검사 뒤에 생성한 파일은 별도로 표시합니다. 기존 검사 설정의 동작은 유지하고 추가 필드와 결과 형식을 문서화합니다.

### 실제 사용 예제

문서 예제는 검사한 문서 묶음을 보존하고, 데이터 예제는 입력 CSV와 가공 과정, 검사한 출력을 연결합니다. 문서 렌더링은 프로젝트 명령으로 연결하는 예제를 제공합니다. 렌더러 실행 가능 여부, 실제 출력 페이지와 구조 검사를 각각 보고합니다.

**완료 기준:** worktree 제거 후에도 보존한 결과물을 대조할 수 있습니다. 필수 결과 누락, 입력이나 출력 변경, 경로 탈출, 실행 중단과 정리 실패를 검사합니다. 구조 검사 통과와 사람이 내용을 읽고 수용한 상태를 구분합니다.

## 4. 수신 확인과 작업 재개

### 검토 메시지 수신

채널에 소비자 식별자와 소비자별 읽음 위치를 추가합니다. 조회, 명시적 수신 확인과 지적 해결을 각각 기록합니다. 같은 메시지를 여러 번 확인해도 결과가 중복되지 않게 하며, 읽음 위치가 바뀌었다는 이유로 지적을 해결 처리하지 않습니다.

승인 철회나 미처리 지적이 있을 때의 종료 조건을 검사합니다. 기존 메시지와 응답 관계를 보존하며 DB 버전을 올리고, 전환을 트랜잭션으로 처리합니다. 동시 소비자, 반복 수신 확인과 전환 실패 시 복구를 테스트합니다.

### 실제 상태를 확인하는 재개 도구

명령 설계안은 `awkit inspect <실행 기록 폴더>`입니다. 기존 검사 결과와 manifest를 읽고 실제 파일의 존재와 동일성을 확인합니다. 사람이 읽는 요약과 JSON으로 기준 버전, 완료한 검사, 결과물, 사라진 근거와 미완료 단계를 보여 줍니다.

중단 전에 남은 `running` 기록은 새 관찰로 확인하기 전까지 불확실한 상태로 표시합니다. 재개 정보는 기존 기준 문서와 실행 기록을 연결해 구성합니다. 현재 작업 상태, 재사용할 지식과 원자료는 각각 맡은 위치에 보존합니다.

### 다른 환경으로 전달

요청 ID, 기준 버전, 선택한 산출물과 응답을 담는 교환 형식을 먼저 정의합니다. 로컬 내보내기와 가져오기로 반복 입력, 잘못된 응답 관계와 버전 불일치를 검사합니다. 원격 연결 방식은 실제로 연결할 두 환경의 인증과 저장 조건을 확인한 뒤 정합니다.

**완료 기준:** 다른 세션이 먼저 읽어도 지정한 소비자가 메시지를 확인할 수 있습니다. 재개 시 오래된 기록과 실제 파일의 차이를 발견하며, 기존 DB 전환에 실패해도 원래 메시지로 복구할 수 있습니다.

## 기능과 함께 반영할 작업 기준

작업마다 목적, 입력, 보존할 결과, 허용 범위와 확인 방법을 정합니다. 자동화에는 필요한 경우 유효 기간과 종료 조건을 적고, 학습에서는 사용자가 직접 수행할 부분과 에이전트의 개입 시점을 정합니다. 수정 작업에서는 채택된 표현과 디자인을 유지할 조건도 다룹니다.

현재 작업 기록, 재사용할 지식과 원자료는 서로의 기준 위치를 연결합니다. 정리와 병합 뒤에는 중요한 결정이 빠지거나 폐기한 규칙이 되살아나지 않았는지 확인합니다. Git으로 관리하는 문서의 버전과 외부 원본이나 앱의 상태도 구분합니다.

기능 구현에 필요한 설명은 해당 단계에서 함께 고칩니다. 일반 원칙만 늘리기보다 실행 예제에서 어떤 실패를 막고 어떤 반복 작업을 줄이는지 확인합니다.

## 검증과 효과 측정

공개 예제와 테스트에는 모의 자료를 사용합니다. 실제 세션에서 발견한 문제는 일반 요구사항으로 옮기며 개인 원문, 이름, 경로와 파일을 배포 자료에 넣지 않습니다.

변경한 기능의 중요한 실패 경로를 먼저 검사하고 배포 묶음마다 지원하는 Windows와 Linux 환경의 전체 테스트와 wheel 설치 검사를 수행합니다. 첫 실행 단계 수, 수동 확인, 수정 횟수, 같은 근거를 다시 찾은 작업과 완료 후 발견된 중요 결함을 기록합니다. 필요한 경우 비슷한 작업에서 기존 절차와 대조합니다.

시간과 사용량에는 확인 범위를 표시합니다. 요청한 모델과 실제 기록된 모델을 구분하고, 토큰, 비용 추정치와 실제 차감액도 따로 다룹니다. 위임 효과는 [위임 지침](../kit/delegation.md)의 측정 기준을 따릅니다. 역할 수나 테스트 수를 작업 품질의 근거로 사용하지 않습니다.

각 기능에는 구현, 실행 예제, 필요한 지침, 실패 진단, 복구 방법과 기존 형식의 전환 안내를 함께 제공합니다. 구현과 검사를 마친 뒤 [CLI 사용법](cli.md), [추가 도구](tools.md), [검증 범위](validation.md)에 실제 동작을 반영합니다.
