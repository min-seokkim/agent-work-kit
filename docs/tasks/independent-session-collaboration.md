## Independent-session collaboration plan

Independent-session coordination is a requested outcome, with the design still open. Roles depend on the work: examples include coordination, planning, research, implementation, testing, review and writing. Allow project-defined roles. Keep session identity separate from role and task: one session may hold several compatible roles, and several sessions may divide tasks within one role. An independent review still requires a separate session. Assign responsibilities, expected outputs, dependencies and file ownership per task, allowing parallel work on separate files and handoffs between roles.

Evaluate creating, attaching to and resuming independent sessions through the capabilities each chosen runtime exposes; subagents alone do not meet this request. Where automatic creation is unavailable, the user opens a session and gives it an initial connection instruction. Route subsequent assignments and reports through supported provider features, with awkit connecting providers and retaining the task evidence needed across interruptions. Local/cloud transport follows selection of two actual environments. Completion requires a real task involving at least three distinct roles to pass through assignment, execution, verification and any correction without manual message relay after setup, with unresolved decisions returned to the user. The current local two-role channel implements only part of this scope; no session launcher or remote transport is implemented.

The owner reports that the current workflow works well. Preserve that working path. The broader scope above is a direction, not a requirement to implement every missing capability now. Sessions make judgments; awkit records requests, reviewed revisions, checks and outcomes. Collaboration across providers is an explicit requirement: the owner values their complementary behavior. Keep each session's context independent and exchange the task material needed; routine sharing of full transcripts would weaken independent review. The recorded local trial used two Codex workers, so it does not establish Claude/Codex interoperability.

The provider integration sequence below takes priority. Preserve these validation cases:

1. Clarify existing command semantics: `post` confirms storage; `wait` returns matching messages; a reply records the sender's reported result. None alone proves successful task completion. Snapshot references remain optional and format-checked by the channel; review procedures supply stronger requirements.
2. Exercise interruption and replay: stop after reading but before replying, resume and find unanswered requests, then repeat a request after its result exists. Use request IDs to detect prior work. Check that cursor movement is not mistaken for processing and that retained results can prevent duplicate actions. These are planned checks, not new recovery guarantees.
3. Run a real task with independent Claude and Codex sessions using the current channel and snapshot workflow. Record the exact clients, versions, models and environments, manual relays or wakes, and interruption outcomes. Establish CLI, IDE and desktop behavior separately; record untested combinations as unverified.

## Lessons from the proposal trial

The [trial recorded with `89549b7`](workflow-review.md) completed assignment, frozen review, correction, checks and final receipt using the existing channel without either session editing the other's product files. The main and reviewer used Codex IDE and Desktop clients and were exposed to the implementation discussion. This supports the local two-role workflow; cross-provider operation, automatic wake-up, recovery after interruption and blinded review remain unverified. The reviewer's later account judged the channel sufficient for this task and reported procedure overhead for small edits.

Preserve this working path before expanding the protocol. Verify session identity from the active runtime when a handoff names an older session. Request judgments against snapshots; retain failed runs as well as corrected runs, classify environment failures separately from candidate defects, and reuse accepted evidence for unchanged content. In this trial, final review found a guide word-limit violation while a separate run failed because Ruff was absent from PATH. They require different corrections.

At closure, confirm the delivered tree equals the checked tree and obtain the recipient's acknowledgement before sending `close`, which prevents further posts. Check for unanswered requests and disclose remaining processes and work. For shared external actions, designate one executor and wait for all affected sessions to finish; task completion never supplies fresh authorization. A deadline for starting closure should leave time for checks and receipts rather than force an abrupt stop. Test interruption immediately before the final receipt and before close without repeating external actions.

Measure active work and waiting separately, using the [usage compatibility plan](usage-log-compatibility.md) where counts are uncertain. Compare the burden of a scoped correction and a larger task before adding acknowledgements, services or routine full reviews. These observations justify validation scenarios, not a larger channel schema.

The [planning and implementation trial](planning-implementation.md) exposed a separate usage issue: polling only `request` recovered unfinished assignments but omitted `notice` messages by design. The implementer repeated an installation comparison before reading a notice containing reusable evidence. Both roles should inspect `new` between work portions for notices and replies, and use `request` to recover unanswered work. Advancing a read position still does not establish handling or completion. This observed duplicate work supports a guidance correction, without changing channel storage or adding an acknowledgement protocol.

## Obligations across several sessions

Status: observed coordination failure; the synthetic evaluation below is complete, and live validation is pending. During the feedback trial on `8c4cd7e`, the planning session ended a completed implementation unit while an application channel still needed a response. The application session also retained a stale no-answer status after replies were stored. The owner identified the broader problem: an agent can forget which session needs which message, including whether a reply is required. These incidents establish missed coordination obligations; they do not establish message loss or prove that a new interface prevents recurrence.

The retained application channel has M-004 and R-004 for the missed request, R-005 and M-005/M-006 for recovery and correction, and M-007/R-008 for the technical assessment. Development-side records are under `.awkit/handoffs/document-feedback-resumed/`. These are local evidence, without the application's private source material. The technical assessment initially classified the incidents as application of existing guidance. The owner's observation adds a product question: how much cross-session state must an agent reconstruct from memory even when each channel works correctly?

At this base, `Channel` operates on one explicitly named SQLite database. `request` returns incoming request kinds and rebuttals without an outgoing reply reference; `new` advances a role's reading cursor. Those functions recover work in a known channel. They do not enumerate all of a session's relationships, represent a notice's follow-up obligation, or establish that a returned contribution was integrated. A session must remember the database, its transport role and the meaning of each pending action. The earlier request-only polling correction remains useful but does not settle this broader question.

Evaluate one session-wide view of explicitly registered relationships and outstanding obligations. Each entry should identify the actual counterpart, channel and local role, relevant task/message or revision, responsible session, next action and reason, and completion evidence. Distinguish an answer owed, a result being awaited, a change that must be forwarded, and a received result awaiting integration. Use existing request/reply records where sufficient; agents must explicitly declare obligations that message kinds alone cannot establish. Do not infer completion from reading, a receipt notice, an ended turn or another unit's closure. Keep informational notices free of automatic reply obligations unless one was actually assigned. Registration must be explicit rather than scanning unrelated projects or collecting full conversations.

The synthetic scenarios use three fictional session identities and two existing channels: an interruption after reading a question, an informational notice and a revised result on another channel, one completed unit while another request remains open, and an explicitly assigned forwarding action in a notice. A later live recovery trial must compare the coordinator's account with predetermined recipients, pending actions and completion conditions. Measure missed obligations, wrong recipients, duplicate replies/actions, unnecessary acknowledgements and manual reminders. Preserve actual active-turn limitations.

The synthetic evaluation at base `8c4cd7e` passed 22 assertions across 26 CLI calls. It reproduced cursor/request differences, notice obligations and an open request surviving another channel's closure. Its maintained record was populated from the expected answers, so it does not demonstrate agent recovery or lower user effort. Five injected trace defects were detected. Local evidence is under `.awkit/handoffs/collaboration-obligations/executor/`.

The provider probes below establish a reusable delivery path, while the recorded cross-channel obligation failures remain. Planning selected `awkit channel status --record <task.json> [--json]` as the next product unit under the owner's continuous-development instruction. It reads one explicit relationship/declaration record and existing channels without posting, advancing cursors or creating a second registry. This decision responds to observed missed obligations and repeated reconstruction; a productivity advantage remains unmeasured.

The selected format separates message-derived protocol state from agent-declared action and disposition. A linked reply supplies a returned result; it does not establish integration. An answer recorded as a notice can be linked as declared evidence while its request remains protocol-unanswered. Closing a channel cannot hide unfinished work. Missing evidence, conflicting declarations and unavailable channels remain visible. The command never interprets notice prose into an action or certifies a declared completion.

## Reuse provider collaboration features

The owner selected a first-party-first approach: use provider messaging, queues, session execution and subagents where available. Preserve the existing provider-neutral channel as a fallback and source of correlated task evidence. The following architecture is a planning proposal, not implemented behavior.

Official sources were inspected alongside the local inventory at base `8c4cd7e`. The ignored coordination checkpoint retains the research timestamp and raw evidence paths; verify current capabilities before a live trial.

Receipt, authoritative task reply and declared result integration remain separate; these tests establish neither arbitrary IDE attachment nor restart-safe exactly-once execution.

awkit should map an explicitly selected provider, runtime endpoint and session ID to a task and its request/reply IDs. Keep the checked revision, responsible session, required next action and completion evidence across provider boundaries. Native features own session execution and their delivery state. Retain only the task material needed for collaboration; full transcript mirroring is unnecessary. Preserve existing SQLite compatibility until a trial establishes a migration need.

The proposed bridge routes a request through the recipient's supported input interface and correlates the returned result with the original request. Codex queue and a Claude channel with a reply tool are initial candidates. Distinguish stored, submitted, replied and applied states according to actual evidence. A send acknowledgement cannot establish task completion. When delivery is uncertain, reconcile before retrying through a second transport; otherwise native delivery plus fallback can execute the same task twice. Preserve each runtime's permission and inbound-message decisions.

The next units are:

1. Use the delivered read-only obligation view to recover registered counterpart, request, reply and declared disposition without changing channels. Select the actual receiving endpoint and supported attachment path before testing active, idle or unavailable peers. Record ownership, client/version, native reference and receipt; do not infer reachability from a status label or repeat completed discovery.
3. Choose a concrete executor caller and durable pre-send/replay boundary before shipping automatic dispatch. The persistence experiment tests local process crashes and contention; it cannot establish power-loss survival or exactly-once remote execution. Do not ship an unused persistence abstraction. Integrate the proven transport only with an actual task caller, preserving each provider's permission decisions.
4. Use the integrated path for one bounded development task. Measure manual relays, missed replies, wrong recipients, duplicate work and setup burden. Evaluate native subagent delegation separately. Use the writing project only for technical feedback under its existing authorization.

Provider reuse remains the execution policy; the status view addresses the remaining cross-channel record gap. An implementation handoff must select its endpoints and acceptance criteria before live probes or product changes. Product ownership of worker lifecycles remains a separate decision from the disposable probes. [OpenAI MCP Events](https://developers.openai.com/plugins/build/mcp-events) documents webhook subscriptions for Work, Cloud and dots; it does not establish that the local Codex IDE accepts those events. Keep that cloud integration separate from the local trial.

Apply these lessons to the next bridge contract: preserve the existing durable channel, use a native wake that points to a pending request when supported, and fetch the actual task under the recipient's existing permissions. Compare this with direct native task delivery before selecting either design. Keep original message IDs across attempts; distinguish wake receipt, task reply and applied result. A fixed wake should identify its automation origin and carry no peer-supplied instruction body.

Extend validation after the first native round trip with lost sender responses, late receipt, interrupted or approval-waiting recipients, restarted owners and duplicate delivery. Reconcile uncertain submissions before another transport is used. Preserve manual-relay and setup measurements. Consider an existing transport component before building another broker, but keep dependency adoption separate from learning its design; the current repository decision adds no third-party collaboration dependency.

Session registration, explicit acknowledgements and file reservations remain conditional extensions. Evaluate automatic wake-up after repeated manual intervention, and remote transport after selecting two real environments that need it. Prefer the existing commands and storage; account for installation, background processes and provider-version maintenance before expanding them. This planning update authorizes no implementation or external dependency installation.
