# Shared artifact storage

## Current status

Planned next product unit. Root owns product selection and this plan; the implementation and independent-review sessions own technical diagnosis and verification. Finish the [storage inspection unit](review-storage.md) through its existing delivery receipt first. No shared-storage implementation or migration is assigned by this document alone.

Next action: prepare a bounded format and compatibility contract for optional shared storage in newly created review runs. Compare the two backend choices below against the same acceptance conditions, obtain one independent upfront assessment, then assign implementation. The coordinator makes the product decision from that assessment; implementation owns checks, CI and installation. Source baseline: `ce019ca`.

## Desired result

Repeated checks can reference one stored copy of identical artifact content while preserving each run's own input identity, configuration, outcome and artifact associations. The first delivery applies only when shared storage is explicitly selected for new runs. Existing copied-artifact runs remain readable and unchanged. Current default collection continues until the optional mode has a completed use trial and a separate default-selection decision.

The [inspection record](review-storage.md#evidence-and-selection) owns the real-use measurement and its limits. The need is to reduce repeated payload storage while retaining evidence that can be retrieved and verified. Inspecting a folder, answering a question or ending a session creates no new record obligation. No background monitor, scheduled recheck, automatic deletion or retention-expiry system is part of this unit.

## Decisions the contract must settle

| Decision | Required result |
|---|---|
| Backend ownership | Prefer a store colocated with the selected review collection unless an alternative meets its portability requirements with less complexity. Both default and externally selected collections have explicit ownership. |
| Format and readers | Define the new opt-in format and how current commands identify supported storage. Preserve legacy reads. Unsupported or missing storage must produce an explicit failure rather than a successful empty result. |
| Retrieval | Verify exact bytes through review commands, compare them with accepted versions, and materialize ordinary files for acceptance, publication and human use. An explicit export can produce a self-contained bundle. |
| Portability | A complete collection can be moved and verified without its original repository path. A single exported run can be verified without the shared store. Specify what copying only one reference-based run requires. |
| Integrity and interruption | Preserve source and artifact identities, detect corruption and missing payloads, and distinguish complete publication from interrupted writes. An interrupted operation must not leave a run falsely verifiable. |
| Storage accounting | Extend storage inspection to count shared payload bytes once while separately reporting each run's references. Preserve the distinction between logical bytes, allocated space and estimated savings. |
| Recovery | Define recovery from interruption and unsupported formats before writing a real user's collection. Keep acceptance and failed-run evidence identifiable. Cleanup or migration remains separately selected work. |

Two backend designs remain to compare: artifact trees retained through explicitly owned Git references, and immutable payloads stored beside the review collection. Existing snapshots alone cannot be assumed to cover files generated or changed during checks. A Git-based design must settle reference lifetime, binary-safe access, repository relocation and export. The alternative must settle object ownership and compatible retrieval without introducing a second source of task state. Confirm source-snapshot retention separately; payload sharing does not establish that source identities remain resolvable.

Ordinary hardlinks do not provide independent evidence when one linked file can be edited. Do not select them as a portable shortcut to immutability. The contract must cover concurrent writers, partial objects, missing references and corruption for whichever backend is selected.

## Acceptance before delivery

- Two new runs containing identical generated bytes retain distinct run records while sharing one payload; changed bytes remain distinct. Measure actual stored logical bytes and metadata overhead on a disposable representative fixture.
- Legacy copied runs still verify, compare and become accepted versions. The shared format supports those outcomes and produces ordinary files for existing publication readers.
- A moved collection and a self-contained exported run verify without the original project path. Missing or corrupt payloads fail visibly.
- Concurrent and interrupted writes preserve completed runs and never claim incomplete evidence as valid. Unsafe references cannot read or write beyond the selected store.
- Storage inspection reports collection bytes and referenced payload bytes without double-counting. No disk-allocation or performance claim is inferred from hash counts.
- Windows and Linux checks, a frozen integration check and a disposable use trial establish the supported behavior. Real existing records are not migration fixtures.

## Subsequent choices

After the optional mode is delivered, assess whether to change new-run defaults and whether an explicit old-run migration is worthwhile. A migration proposal must identify affected evidence paths, demonstrate recovery and explain any loss of standalone access. Deletion and expiry are not implied by shared storage. Keep two-environment continuation and shared-context discovery in the [roadmap](../roadmap.md); they do not expand this unit.
