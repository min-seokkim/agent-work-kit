# 검증 범위

0.2.0을 바탕으로 한 현재 소스와 이전 버전의 검사 결과를 구분해 기록합니다. 배포, 변경본 검사와 발행은 로컬 모의 프로젝트에서 검사했고, 사용량 집계는 실제 Claude Code 기록으로도 확인했습니다. 실제 서버 배포, 업무 DB, 외부 에이전트 호출은 여기에 들어 있지 않습니다.

[역할과 범위](scope.md)의 제품 결정과 [개발 계획](roadmap.md)의 후속 작업은 아래 검사 결과와 구분합니다. 사용량 수집 연결, 수신자별 채널 상태와 작업별 근거의 자동 연결은 아직 검증 대상에 포함되지 않았습니다.

전체 검사는 `python -m unittest discover -s tests -v`로 실행했습니다. Windows의 시간 초과 시 하위 프로세스 정리도 통과했습니다. 첫 실행 예제, 결과물 보존, 사용량 형식 2와 영어 메시지는 아직 Windows에서 돌려 보지 않았으며, CI의 Windows 작업에 데이터 예제의 실패와 재검사를 추가해 두었습니다. 브라우저 캡처, 실제 장치 적용과 외부 제출은 실행하지 않았습니다. 공통 키트 자체에는 Python이 필요 없습니다.

결과물 보존 테스트의 첫 Windows 실행에서는 Git의 줄바꿈 변환 때문에 원본 바이트와 worktree의 바이트가 달라 비교가 실패했습니다. 해당 테스트 저장소에 `core.autocrlf=false`를 지정해 입력 조건을 고정한 뒤 통과했습니다. 지금은 `kit init`과 `kit example`이 새로 만드는 저장소에 같은 설정을 넣으므로 예제 저장소에서는 이 변환이 일어나지 않습니다. 이미 있는 저장소의 설정은 바꾸지 않습니다. 예제는 실제로 검사한 worktree 파일의 바이트와 해시를 보존합니다. 이 변경 뒤의 Windows 실행 결과는 CI로 확인합니다.

## 동작별로 검사하는 내용

### 검토 채널

여러 프로세스가 동시에 써도 메시지 번호와 본문이 보존되는지 봅니다. 응답이 올바른 메시지에 붙는지, 읽은 위치가 제대로 움직이는지, 닫힌 채널에 쓰기를 거부하는지, 본문으로 다른 메시지의 제목을 흉내 낼 수 없는지도 검사합니다. 0.2.0에서는 다른 세션이 쓰기 잠금을 쥐고 있어도 대기와 출력이 막히지 않는지, 빈 본문을 거부하는지, `--body`와 `--body-file`로 한글 본문이 그대로 전달되는지를 더했습니다.

### 배포 실행기

정상 갱신, 같은 버전 재요청, 잘못된 대상, 백업 실패를 다룹니다. 배포가 실패했는데 이전 버전만 응답하는 상황, 자동 복귀와 그 실패, 시간 초과, 동시 실행 잠금, 서로 다른 두 프로젝트의 상태 분리도 검사합니다. 0.2.0에서 더한 검사는 다음과 같습니다.

- 현재 버전이 고장 났을 때 일반 배포는 멈추고 `--allow-unhealthy-current`로는 배포되는지
- 고장 난 버전으로 자동 복귀하지 않는지, 같은 버전을 다시 배포하는지
- `rollback`을 거듭하면 이력을 따라 뒤로 가는지, 현재 버전이 고장 났어도 돌아가는지
- `reconciled-unhealthy` 다음의 복구, 0.1.0 상태 폴더에서 이력을 되살리는지
- 시간 초과 때 배포 명령이 띄운 하위 프로세스까지 종료하는지, 단계별 출력이 남는지

### 변경본 고정과 격리 검사

스냅샷이 지정한 파일의 추가, 변경, 삭제만 담는지 확인하고, 실제 HEAD와 index의 바이트, 작업 파일 상태가 그대로인지 대조합니다. 격리 검사는 고정한 버전으로 실행되는지, 준비 단계가 실패하면 멈추는지, 검사 하나가 실패해도 나머지를 계속 돌리는지 봅니다. 실행마다 다른 폴더를 쓰는지, 정상 종료 때 자기 worktree만 정리하는지, 시간 초과 때 근거와 worktree를 남기고 하위 프로세스를 종료하는지도 검사합니다.

단계별 `cwd`는 공백이 있는 하위 폴더, 앞선 준비 단계가 만든 폴더와 기본 루트 실행을 검사합니다. 잘못된 경로는 실행 전에 거부하며, 없는 폴더나 worktree 밖을 가리키는 연결 경로는 해당 단계의 실패로 기록합니다. 준비 단계의 폴더 오류가 검사를 막고 검사 단계의 폴더 오류 뒤에는 나머지 검사가 계속되는지도 확인했습니다.

[하위 폴더 예제](../examples/review/subdirectory.toml)를 테스트용 Git 저장소의 스냅샷으로 실행했습니다. 원래 작업 파일을 이후에 바꿔도 스냅샷의 내용을 검사하며, worktree 정리 후에도 실행 기록 폴더에 파일과 일치하는 SHA-256이 남았습니다. 실패한 검사에서 기록 폴더에 쓴 진단 자료도 보존되는지 확인했습니다.

### 결과물 보존과 대조

`artifacts` 패턴에 맞는 파일이 실행 기록 폴더에 복사되고 크기와 SHA-256이 `result.json`과 manifest에 남는지, 패턴에 맞지 않는 파일은 복사되지 않는지 봅니다. `required_artifacts`가 없으면 검사 명령이 통과했어도 실패로 기록하는지, 검사가 실패한 실행에서도 진단 파일을 보존하는지, 연결 파일은 건너뛰고 `skipped_artifacts`에 적는지, 잘못된 패턴은 실행 전에 거부하는지 확인합니다. `verify`는 변경·누락·추가 파일을 각각 보고하고, 다른 스냅샷의 manifest와 `running` 상태의 기록을 구분하는지 검사합니다.

### Git 추적과 프로젝트 살펴보기

`kit init`과 `kit example`이 저장소가 없는 폴더에 저장소를 만들고 해당 폴더만 commit하는지, commit 이력이 있는 저장소와 없는 저장소 안에서 각각 예제 폴더만 commit하고 사용자의 다른 파일은 건드리지 않는지, 스테이징된 변경이 있으면 commit하지 않고 이유를 돌려주는지, `--no-git`이면 아무것도 만들지 않는지 봅니다. `review snapshot`, `check`, `compare`는 저장소가 아닌 폴더와 commit이 없는 저장소를 거부하고 `.git`을 만들지 않는지 확인합니다. 기존 저장소의 하위 폴더에 만든 예제에서 README의 명령이 그대로 동작하는지도 봅니다. `check HEAD`가 그 하위 폴더에서 명령을 실행해 의도한 결함을 찾고, 스냅샷과 보존한 결과물과 `compare`의 경로가 예제 폴더 기준으로 나오는지 확인합니다.

`kit scan`은 `package.json` scripts, `pyproject.toml`의 ruff 설정과 tests 폴더, Makefile 대상, GitHub Actions의 `run:` 줄, 문서 폴더를 찾아 보고하고 TOML로 읽히는 검사 설정 초안을 내는지, 키트 적용표의 "Start here" 다섯 항목 중 채운 수와 Git 상태를 세는지 검사합니다.

### 전달 실행기의 선택 명령

`backup`과 `rollback`이 없는 설정으로 첫 전달이 통과하는지, `rollback` 실행을 거부하는지, 적용 중 실패가 `failed-unrecovered`와 `recovery.skipped`로 기록되고 다음 실행을 막는지, `reconcile`로 풀리는지, `rollback` 없이 `auto_rollback`을 켠 설정을 거부하는지 봅니다.

### 채택본 추적

`accept`가 검증된 실행의 결과물과 manifest, 출처 기록을 `.awkit/accepted/<label>/`에 복사하고 같은 label을 다시 채택하면 이전 것을 바꾸는지, 보존 파일이 없거나 변조된 실행과 잘못된 label을 거부하는지 봅니다. `compare`는 작업 폴더와 새 실행의 결과물을 각각 채택본과 비교해 `same`, `changed`, `missing`을 보고하고, 바뀐 텍스트 파일에 diff를 붙이는지, 없는 label을 거부하는지 확인합니다.

### 첫 실행 예제

세 예제를 임시 폴더에 만들고(만들 때 commit까지 됨) 실제로 실행합니다. 분석 예제는 가정을 고친 뒤 통과한 실행을 채택하고, 환산 계수를 바꾼 다음 실행이 채택본과 어디서 달라졌는지 `compare`가 보고하는지도 봅니다. 처음 검사는 실패하고 로그에 결함이 나오는지, 입력을 고친 스냅샷으로 다시 검사하면 통과하고 결과물이 보존되는지, 스냅샷이 브랜치를 바꾸지 않는지 봅니다. 예제 폴더가 이미 있으면 만들지 않는지, 모든 파일이 복사되는지도 확인합니다. 저장소 전체 링크 검사는 문서 예제의 의도한 깨진 링크 하나만 남는지 고정합니다.

### 문서 발행

같은 입력을 다시 발행하면 같은 버전을 쓰는지, 바뀐 입력은 새 버전으로 발행되는지, 이전 버전으로 돌아가는지 확인합니다. 깨진 링크, 없는 앵커, 빠진 CSS 자원, 발행 폴더 밖을 가리키는 경로, 다른 프로젝트의 폴더, 변조된 파일, 목록에 없는 파일은 모두 거부해야 합니다. 진입점을 바꾸는 도중 오류를 일부러 일으켜도 이전 진입점이 살아 있는지, 다른 파일이 든 출력 폴더를 덮어쓰지 않는지도 봅니다.

### 화면 캡처

실제 로컬 HTTP 서버를 띄우고 브라우저로 전체 화면 PNG와 검토 시트를 만듭니다. 시트에 넣는 화면 이름이 HTML로 해석되지 않는지, 잘못된 설정을 거부하는지도 검사합니다.

### 역할 파일과 사용량 집계

역할 양식이 다섯 역할을 모두 담고 등급과 권한이 맞는지, Claude Code 역할 파일에 등급별 기본 모델과 읽기 전용 도구 제한이 들어가는지 봅니다. Codex 역할 파일은 지정한 등급에만 모델이 들어가는지, `sandbox_mode`를 넣지 않는지, `top`을 주면 `analyst_top`이 생기는지, 만든 파일이 TOML로 읽히는지 확인합니다. 이미 있는 역할 파일을 덮어쓰지 않는지, 형식이 틀린 모델 지정을 거부하는지도 검사합니다.

사용량 집계는 Claude Code에서 여러 줄로 나뉜 응답을 한 번만 세는지, 자식 에이전트 기록을 따로 묶는지, 합성 메시지와 쓰다 만 마지막 줄을 건너뛰는지 확인합니다. 토큰 필드가 없거나 값이 잘못된 기록은 `0`이 아니라 `null`과 `missing`·`invalid` 횟수로 나오는지, 합계의 `complete`가 거짓이 되는지, 파일 중간의 손상된 줄과 끝의 미완성 줄을 따로 세는지도 검사합니다. 사람이 쓴 메시지만 세고 도구 결과와 자식 에이전트 지시는 세지 않는지, 기록의 timestamp로 첫 기록과 마지막 기록 사이의 분을 구하는지, Codex의 `user_message` 이벤트를 세는지도 확인합니다. Codex의 사용자 메시지 필드 이름은 모의 기록 기준이며 실제 파일로는 확인하지 않았습니다. 이 도구를 만든 Claude Code 세션의 실제 기록도 읽어 봤습니다. 확인 시점에 376줄이 156번의 호출로 묶였습니다. Codex는 `turn_context`의 모델과 추론 수준, 마지막 누적 `token_count`에서 토큰을 읽는지 모의 기록으로 검사합니다. 이 모의 기록은 실제 기록에서 확인된 필드 이름으로 만들었지만, 최신 Codex 기록 파일로는 아직 돌려 보지 않았습니다.

### 공통 키트와 문서

`kit init`이 키트를 빠짐없이 복사하는지, 이미 있는 폴더를 건드리지 않는지, 경로가 섞인 폴더 이름을 거부하는지 봅니다. 저장소의 루트 문서와 `docs/`, `kit/`, `examples/`의 상대경로 링크, 복사한 키트 안의 링크가 실제 파일을 가리키는지도 자동으로 확인합니다. 링크 검사는 `.venv` 같은 숨김 폴더와 의존성 폴더를 건너뛰며, 그 안의 깨진 링크를 무시하고 관리 문서의 깨진 링크는 찾는지 회귀 테스트로 고정했습니다.

## 배포물

릴리스 파일은 `scripts/build_release.py`가 만듭니다. wheel에는 실행 코드와 공통 키트가, 키트 ZIP에는 `kit/` 폴더의 Markdown만 들어갑니다. 소스 전체는 GitHub이 태그마다 만들어 주는 압축 파일을 씁니다. 원래 이 도구를 만든 프로젝트의 이름이나 특정 날짜, 개발 PC의 경로는 배포물에 넣지 않았습니다.

공통 키트를 별도 프로젝트 폴더에 넣고 기존 지침 파일을 바꾸지 않은 채 쓸 수 있는지도 확인했습니다. [프로젝트별 적용 예시](../kit/examples/project-profiles.md)는 시스템 프로그램, SDK, 펌웨어, 확장 프로그램, 배치 처리, 서비스와 문서의 완료 조건을 설명합니다. 이 예시 자체는 각 환경에서 빌드·설치·제출한 결과를 뜻하지 않습니다.

## 실제로 적용할 때 남는 확인

격리 검사의 worktree는 DB와 포트, 외부 서비스를 나눠 주지 않습니다. 검사 명령과 로그 관리는 프로젝트 몫입니다. 시간 초과 때 로컬 하위 프로세스는 정리하지만, 원격 서버에서 이미 시작된 작업은 멈추지 못합니다. 스냅샷에는 비밀정보 검사나 장기 보존 기능이 없습니다.

문서 발행은 신뢰하는 HTML 빌드 결과물을 전제로 합니다. Markdown 변환, JavaScript가 만드는 주소, HTML 정화, 브랜치별 대기열, 오래된 발행 요청 차단은 들어 있지 않습니다. 잠금은 같은 PC에서 같은 로컬 폴더를 쓰는 경우에만 통합니다.

화면 캡처가 자동으로 찾는 문제는 가로 넘침과 화면 밖으로 나간 조작 요소뿐입니다. 접근성이나 업무 흐름이 제대로인지는 판단하지 않습니다. 실제 배포에서는 대상 서버 잠금, 이미지 식별, 백업 복원, 이전 앱과 데이터의 호환성을 따로 확인해야 합니다.

명령의 자세한 조건은 [CLI 사용법](cli.md)과 [추가 도구](tools.md)에, 다음 후보는 [개발 계획](roadmap.md)에 있습니다.
