# Connect the Kit to a Project

Use this once in a project, after `awkit kit init`, while `done` or `recipient` in the `[kit]` table of `checks.toml` is still empty. The kit has three layers. This computer holds awkit and the guides, as skills in the user folder that `awkit kit skills` writes; `awkit kit guide NAME` prints any guide for an agent without skills. The project commits only what finishing means there: `checks.toml` with its `[kit]` table, and `rules.toml`. The hooks and `.awkit/` stay in this clone, because hooks run code. Connecting fills the table and the checks from what the project already has. [Example profiles](examples/project-profiles.md) show such answers for several kinds of project.

Read before adding anything. Run `awkit kit scan` in the project folder. Its first line is the number of words the kit adds to every session. The report lists the project's instruction files, skills and method bundles, hooks, memory and record locations, completion gates, manifests, the commands CI already runs and the Git state. Treat every suggested command as unverified: the scan reads file names and manifests, not behavior.

Then do the following, and record each result rather than assuming it:

1. Fill `[kit]` from the scan and from one question to the user. `done` is one sentence saying what counts as done in this project; `recipient` is who or what receives the result. Point to where the project already states a command, convention or decision (a section of its instructions, a CI file, a Makefile) instead of copying it: a copy goes out of date and doubles what agents read. Do not invent a build or deployment step the project does not have. Leave `version` as `kit init` wrote it; `awkit doctor` compares it with the installed awkit.
2. Keep state where the project keeps it. `records` names that place: a tracker, a memory file, a planning folder or the project's own documents; `kit init` fills it from what the scan found. Task state, decisions and checkpoints go there; the record templates in [task records](protocol.md) are for a project without one. Do not write to memory that the agent's own tools manage, such as Claude Code's automatic memory.
3. Check the commands in `checks.toml`, which `kit init` drafted from the scan. If there are no `[[checks]]` entries, identify an existing project check or define a check for the agreed task before running `review check`; record unsupported work explicitly. `awkit doctor` validates the configuration without executing it. Use `awkit review check HEAD --config checks.toml` only when HEAD contains the intended source and command dependencies. Otherwise [snapshot explicitly selected current inputs](reference.md#snapshot) and check that revision with the same configuration. Configuration is read outside the snapshot and hashed; include it if a check reads it as an input. Run the commands once and keep those that actually run here. List the files a passing run must produce under `artifacts` and `required_artifacts`. When the project has a completion gate, use the gate's check command here too, so the gate and `awkit review check` judge the same thing.
4. Write the delivery stages the project really uses (build, test, install, submit, accept, verify in use) into `done`, or point to where the project records them; [Delivery](delivery.md) says what each needs.
5. Check `rules.toml` with the user. `kit init` called `awkit kit hooks`, which drafts the rules the hooks apply and adds a handler running `awkit hook` beside the project's own hooks, and the commit identity check after any commit-msg hook the project has. The rules block commits whose author or trailers differ from the history, stop the agent from finishing with changed files that have no passing check (left out when the project has a completion gate), and give one line of the matching guide when a search, an upload, a subagent or a Markdown edit starts. Show the user the rules and remove those they do not want. When `awkit doctor` reports that no hook runs awkit, run `awkit kit hooks --git --claude --codex`.
6. Commit `checks.toml` and `rules.toml`; `kit init` commits nothing unless run with `--commit`, and never creates a repository, so ask the user before running `git init` in a folder that is not one. The review commands do not create repositories or commits either: if `awkit review` reports that the folder is not a Git repository or has no commit, commit the files first. When the user wants the project's instructions to point at the kit, add the line `kit init` printed to `AGENTS.md` or `CLAUDE.md`; awkit never writes there.

Hook settings created by this install stay out of ordinary commit candidates through exact rules in `.git/info/exclude`. Existing settings keep their Git treatment. Use the [snapshot recipe](reference.md#snapshot) as written; `check done` includes user settings that Git tracks or offers to track.

`awkit kit remove` takes out the `[kit]` table and, through `kit hooks --remove`, the hooks, their exclude rules and `rules.toml`; the `.awkit/` rule stays while check records remain. Unchanged original files are restored byte for byte, and later user edits stay. `kit remove --user` deletes the skills from the user folder. For a newer kit, update awkit and run `awkit kit skills` again: it regenerates the skills and leaves `checks.toml` as it is. With a folder copied by an earlier awkit (`kit init --copy`), the profile is `templates/project.md` in that folder; `awkit doctor` says when the folder can go.

Ask before touching credentials, remote targets or settings outside the project folder.

Prevents: F7, F9, F11, F12, F29.
